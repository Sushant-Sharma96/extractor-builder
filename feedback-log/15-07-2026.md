# 1. Converter Engine Issues

## A. Hover Effects / Missing Lovable Classes

### Problem

Hover effects are not working correctly because the converter ignores
some original Lovable utility classes.

Example:

``` html
class="h-full w-full object-cover object-top transition duration-700 group-hover:scale-105"
```

Every class is important.

The original Lovable classes are the **source of truth**.

The converter must preserve every required utility class unless it is
intentionally transformed.

------------------------------------------------------------------------

## B. Typography Extraction Issues

The following properties are repeatedly getting lost:

-   line-height
-   margin
-   padding
-   font-size
-   color

Example:

``` html
<h2 class="mt-6 font-display text-4xl leading-tight md:text-5xl">
Strategy sets direction.
<em class="text-gradient-gold">Story sets it in motion.</em>
</h2>
```

Generated CSS:

``` css
.md\:text-5xl{
    font-size:var(--text-5xl);
    line-height:var(--tw-leading,var(--text-5xl--line-height));
}
```

### Expected Direction

The converter should not rely only on CSS extraction.

Typography should be scanned from the **DOM and computed styles first**,
then converted into CSS.

DOM should become the primary source of truth.

------------------------------------------------------------------------

## C. Body Styles Missing

Important `<body>` properties are frequently missing.

Examples:

-   background-color
-   background-image
-   margin
-   padding
-   font-family
-   font-size
-   line-height
-   spacing

Since body is the root element, missing properties create cascading
design differences across the entire page.

------------------------------------------------------------------------

## D. Scroll Animations

Scroll animations do not behave the same as the original Lovable
website.

Possible reasons:

-   CSS mismatch
-   Missing JS
-   Missing keyframes
-   Wrong selector mapping
-   Wrong trigger

The analyzer must understand runtime behaviour instead of only copying
styles.

------------------------------------------------------------------------

## E. Font Handling

Current issue:

Only one font gets imported.

Additional fonts silently fall back.

Some Lovable websites use multiple font families.

### Standard Variables

Use:

``` css
--body-font-family
--heading-font-family
```

Default:

-   Body → `--body-font-family`
-   Headings (H1-H6) → `--heading-font-family`

However...

Some headings intentionally use `--body-font-family`.

The converter must detect this automatically instead of assuming all
headings use heading fonts.

Also share on response as well

### Additional Requirements

-   Detect every font used.
-   Import every Google Font.
-   Return detected font names in the response.
-   If a font is not supported by Google Fonts:
    -   Generate required `@import` if available.
    -   Return a warning flag.
    -   Inform the user that design may vary because an external font is
        being used.

# Product Direction (My Suggestions)

Current project already contains Bootstrap and existing CSS.

This creates conflicts.

Future solution:

When a user pastes a Lovable URL, provide two export modes.

## Option 1 - Pixel Perfect

Generate additional protective CSS.

Purpose:

-   Avoid project CSS conflicts.
-   Preserve exact design.
-   Support Bootstrap environments.

CSS size will increase.

------------------------------------------------------------------------

## Option 2 - Adjustable Design

Generate original Lovable CSS only.

Advantages:

-   Smaller CSS.
-   Easier maintenance.
-   Better long-term scalability.
-   No unnecessary override CSS.

------------------------------------------------------------------------

Also provide:

-   Variable-based CSS
-   Raw CSS

Allow the user to choose.

# Production Constraints (Most Important)

The converter is already LIVE.

The team is actively using it.

There is no staging environment.

Every deployment immediately affects production.

I have already tested around 20 Lovable microsites.

From this point onward:

-   Existing working behaviour must never break.
-   Improvements must not introduce regressions.
-   Old exports should continue to work.
-   Every change should be tracked.
-   The system should learn from previous failures.

Before every deployment we should consider:

-   Regression pipeline
-   Automated testing
-   React testing
-   DOM snapshot comparison
-   Visual regression
-   Behaviour verification
-   Change tracking

The product should gradually become self-improving by validating
previous failures before every deployment.
