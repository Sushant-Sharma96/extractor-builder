## PART 1 — The Complete Figma Design Model

This section is sourced from Figma's own official REST API type definitions (`github.com/figma/rest-api-spec`) and official developer documentation, deliberately going beyond our 5 cached fixture files — the goal is "what can ANY Figma file contain," not "what do our 5 test files contain."

### 1.1 The core architectural fact: Figma's schema is trait-based, not a single flat node shape

This is the single most important structural fact for how we should represent designs internally, and it is worth stating before the property inventory: **Figma does not define one "Node" type with every possible field.** Its own official types are composed from ~16 orthogonal traits, and every concrete node type (FRAME, TEXT, ELLIPSE, ...) is built by mixing in whichever traits apply to it:

| Trait | Carries | Applies to |
|---|---|---|
| `IsLayerTrait` | id, name, type, visible, locked, scrollBehavior, rotation, componentPropertyReferences, boundVariables | every node |
| `HasLayoutTrait` | absoluteBoundingBox, absoluteRenderBounds, constraints, relativeTransform, size, layoutAlign, layoutGrow, layoutPositioning, min/maxWidth, min/maxHeight, layoutSizingHorizontal/Vertical, grid-cell placement fields | every node with geometry |
| `HasFramePropertiesTrait` | clipsContent, background, layoutGrids, overflowDirection, layoutMode + all Auto Layout fields | FRAME, COMPONENT, COMPONENT_SET, INSTANCE — **explicitly NOT GROUP** |
| `HasBlendModeAndOpacityTrait` | blendMode, opacity | nodes that render paint |
| `HasGeometryTrait` (extends fills/strokes) | fillOverrideTable, fillGeometry, strokeGeometry, strokeCap, strokeMiterAngle | vector-ish shapes |
| `MinimalFillsTrait` / `MinimalStrokesTrait` | fills/styles, strokes/strokeWeight/strokeAlign/strokeJoin/strokeDashes | shapes |
| `IndividualStrokesTrait` | individualStrokeWeights (top/right/bottom/left) | rectangles/frames |
| `CornerTrait` | cornerRadius, cornerSmoothing, rectangleCornerRadii | rectangle-like shapes — **NOT ellipses** (see 1.3) |
| `HasEffectsTrait` | effects[] | shapes |
| `HasMaskTrait` | isMask, maskType, isMaskOutlined | shapes |
| `HasChildrenTrait` | children[] | containers |
| `ComponentPropertiesTrait` | componentPropertyDefinitions | COMPONENT_SET |
| `TypePropertiesTrait` | characters, style, characterStyleOverrides, styleOverrideTable, lineTypes, lineIndentations | TEXT |
| `TransitionSourceTrait` | transitionNodeID, interactions | prototyping |
| `DevStatusTrait` | devStatus | Dev Mode |

**Why this matters for us:** our own internal representation (NDG) currently gives every node the same flat shape (`box`, `paints`, `strokes`, `effects`, `geometry: {...}`, `attributes: {...}`) regardless of node type, with the caller expected to know which fields are meaningful for which type. Figma's own model instead makes "does this concept even apply to this node" a structural, checkable fact (a GROUP literally cannot have `cornerRadius` — the type doesn't include `CornerTrait`). This is a candidate root cause in its own right: **our ingest layer has no way to distinguish "this field is absent because Figma didn't send it for this node type" from "this field is absent because of a bug in our own reading of it"** — both currently just look like `null`. Every silent-drop bug found this session (`textAlignHorizontal` read from the wrong nesting level, `strokes` moved to the wrong location between ingest and the final graph node, ELLIPSE roundness having no numeric field at all) is a variant of this same blind spot.

### 1.2 Complete node type list (confirmed from Figma's own REST API spec)

`DOCUMENT`, `CANVAS`, `FRAME`, `GROUP`, `COMPONENT`, `COMPONENT_SET`, `INSTANCE`, `BOOLEAN_OPERATION`, `VECTOR`, `RECTANGLE`, `ELLIPSE`, `LINE`, `STAR`, `REGULAR_POLYGON`, `TEXT`, `TEXT_PATH`, `SHAPE_WITH_TEXT`, `SECTION`, `SLICE`, `CONNECTOR`, `TABLE`, `TABLE_CELL`, `STICKY`, `WIDGET`, `EMBED`, `LINK_UNFURL`, `WASHI_TAPE`, `TRANSFORM_GROUP`.

Our empirical corpus (5 real cached files, ~1,160 nodes, audited earlier this session) only ever exercised 8 of these: GROUP, LINE, TEXT, VECTOR, FRAME, ELLIPSE, RECTANGLE, CANVAS. **20 node types have zero coverage in anything we have ever tested against.** Of particular note for "what would break us next":
- `COMPONENT` / `COMPONENT_SET` / `INSTANCE` — real component/variant systems, completely unexercised. Any design built from a real component library (the single most common professional Figma workflow) has never touched our pipeline.
- `SECTION` — Figma's canvas-organization node, increasingly common in real files, never seen.
- `BOOLEAN_OPERATION` — union/subtract/intersect/exclude shape combination, never seen.
- `TABLE` / `TABLE_CELL` — real tabular layout (as opposed to our own row-set heuristic that guesses "table-like" structure from geometry), never seen.
- `STICKY`, `WIDGET`, `EMBED`, `LINK_UNFURL`, `CONNECTOR` — FigJam-style nodes; unlikely in product UI files but possible if a canvas mixes FigJam content in.

### 1.3 Corner rounding — confirmed two independent mechanisms (already found the hard way this session)

- `cornerRadius` (single number) or `rectangleCornerRadii` (4-element array, one per corner — a design can round only some corners) — both live on `CornerTrait`, present on RECTANGLE/FRAME/COMPONENT/INSTANCE-like nodes.
- `ELLIPSE` has **no `CornerTrait` at all** — roundness is intrinsic to the node type. This is not a special case Figma "forgot" to give a radius field to — it's a structural consequence of the trait system: ellipses were never given `CornerTrait` because the concept doesn't apply to them the same way.
- Also: `cornerSmoothing` (0–1, "squircle" rounding) exists as a third, distinct mechanism, real in Figma's model, unexercised in our fixtures.

### 1.4 Fills — five real paint types, plus nuances beyond "what color"

`SOLID`, `GRADIENT_LINEAR`, `GRADIENT_RADIAL`, `GRADIENT_ANGULAR`, `GRADIENT_DIAMOND`, `IMAGE`, `VIDEO`. Beyond the type, real designs commonly stack **multiple fills on one node** (a solid color plus an image overlay is a completely ordinary Figma pattern, e.g. a photo with a color wash), and each fill entry carries its own `visible`, `opacity`, and `blendMode` independent of the node's own opacity/blend mode.

### 1.5 Strokes — richer than "width + color"

`strokeAlign` (`INSIDE` | `OUTSIDE` | `CENTER`), `strokeCap` (a surprisingly large enum: NONE, ROUND, SQUARE, LINE_ARROW, TRIANGLE_ARROW, DIAMOND_FILLED, CIRCLE_FILLED, TRIANGLE_FILLED, and six WASHI_TAPE variants), `strokeJoin` (MITER/BEVEL/ROUND), `strokeDashes` (dash pattern array — dashed/dotted borders), `strokeMiterAngle`, and **per-side stroke weights** exposed two ways: `individualStrokeWeights: {top,right,bottom,left}` (REST API) and `strokeTopWeight`/`strokeBottomWeight`/`strokeLeftWeight`/`strokeRightWeight` (Plugin API naming) — both real, both meaning "this border is not uniform on all four sides."

### 1.6 Effects

`DROP_SHADOW`, `INNER_SHADOW`, `LAYER_BLUR`, `BACKGROUND_BLUR` are the confirmed real effect types (each with color/offset/radius/spread for shadows, radius for blurs). A node can carry a **list** of effects, not just one (a card can have both a drop-shadow and a background-blur simultaneously).

### 1.7 Text — considerably richer than font/size/weight

Beyond the typography fields already partially handled (fontFamily/Size/Weight/letterSpacing/lineHeight): `textAlignHorizontal` (LEFT/CENTER/RIGHT/JUSTIFIED — confirmed today, was silently always-null due to a wrong-nesting-level read bug), `textAlignVertical` (TOP/CENTER/BOTTOM — same bug, still unread anywhere downstream), `textAutoResize` (NONE/WIDTH_AND_HEIGHT/HEIGHT/TRUNCATE), `textCase`, `textDecoration` (UNDERLINE/STRIKETHROUGH) **plus** `textDecorationColor`, `textDecorationOffset`, `textDecorationStyle` (SOLID/DOUBLE/DOTTED/DASHED), `textDecorationSkipInk`, `textDecorationThickness` — a real underline is a small design system in itself, not a boolean. Also: `paragraphSpacing`, `paragraphIndent`, `listSpacing`, `lineTypes`/`lineIndentations` (real ordered/unordered list structure), `hangingPunctuation`, `hyperlink`, and per-character overrides via `characterStyleOverrides`/`styleOverrideTable` (confirmed already handled correctly by our renderer via `textRuns()`).

### 1.8 Auto Layout — including a mode we don't emulate at all

`layoutMode`: `NONE` | `HORIZONTAL` | `VERTICAL` | **`GRID`**. Our entire "grid-track" mode is a *guessed* concept, reverse-engineered from raw geometry — but Figma has a **real, native, declarative Grid Auto Layout mode** with its own explicit fields: `gridRowCount`, `gridColumnCount`, `gridRowGap`, `gridColumnGap`, `gridColumnsSizing`, `gridRowsSizing`, `gridChildHorizontalAlign`, `gridChildVerticalAlign`, `gridRowSpan`, `gridColumnSpan`, `gridRowAnchorIndex`, `gridColumnAnchorIndex`. If a real design uses Figma's own Grid Auto Layout, we currently have no path that reads any of this — we'd fall through to the same geometry-guessing machinery used for freeform content, discarding a fully explicit answer Figma already gives us.

Beyond HORIZONTAL/VERTICAL basics: `primaryAxisSizingMode`/`counterAxisSizingMode` (FIXED/AUTO), `primaryAxisAlignItems` (MIN/CENTER/MAX/SPACE_BETWEEN), `counterAxisAlignItems` (MIN/CENTER/MAX/**BASELINE**), `layoutWrap` (NO_WRAP/WRAP) plus `counterAxisSpacing`/`counterAxisAlignContent` for the wrapped-row gap once wrapping is on, `itemReverseZIndex`, `strokesIncludedInLayout`. Per-child: `layoutAlign`, `layoutGrow`, `layoutPositioning` (AUTO/**ABSOLUTE** — a child can explicitly opt out of the Auto Layout flow while its siblings participate), `layoutSizingHorizontal`/`layoutSizingVertical` (FIXED/HUG/FILL — this is Figma's own direct equivalent of CSS `width:auto` vs `fit-content` vs `100%`, and we currently derive an approximation of this from raw box comparison instead of reading it directly when it's present).

### 1.9 Components and Instances

`componentId`, `mainComponent`, `componentPropertyDefinitions` (on a COMPONENT_SET — the full set of variant axes and their possible values, e.g. "size: sm|md|lg", "state: default|hover|disabled"), `componentProperties` (which specific values THIS instance has for those axes), `overrides` (exactly which properties of the instance differ from its main component — text content, a swapped icon, a toggled visibility), `variantProperties`. This is a complete, structured description of *why* a given instance looks the way it does relative to its component family — currently entirely unused by our pipeline (0 real occurrences in our fixture corpus, but this is the single most common pattern in any professionally-maintained design system).

### 1.10 Masks, clipping, overflow

`isMask` / `maskType` (ALPHA/VECTOR — one layer clips the ones below it in the same group) and `clipsContent` (a frame crops children that overflow its bounds) are two *different* mechanisms for "hide what's outside this shape," both real, both currently unimplemented anywhere in our per-node rendering (confirmed: `clipsContent` is read at the page-root/canvas level only, never per-node).

### 1.11 Rotation & transform

`rotation` (radians), `relativeTransform` (a full 2×3 affine matrix — can encode rotation, skew, and non-uniform scale together, not just rotation). Figma's `absoluteBoundingBox` for a rotated node is the **post-rotation, axis-aligned bounding box** (confirmed empirically this session: a 90°-rotated 411×42 node reports an absoluteBoundingBox of 42×411 — dimensions swapped). This has a direct, non-obvious consequence for any renderer that positions nodes by their own absolute box and then ALSO wants to apply a CSS `transform: rotate()` on top: doing so for a non-180° rotation double-transforms the element, because the box is already rotated. (Full detail in Part 4/5 below — this was solved correctly this session, but the reasoning is subtle enough to be a real risk for the next 1,000 files if not written down.)

### 1.12 What a "wrapper" node can mean structurally (relevant to Part 3, Skeleton)

Across real Figma files there are at least four structurally distinct reasons a childless-looking or single-child GROUP/FRAME exists in the tree, and Figma's raw JSON does not label which one it is — it must be inferred:
- **Auto-layout container** — has `layoutMode` set; a genuine layout instruction.
- **Boolean/vector composition wrapper** — groups multiple VECTOR paths into one visual shape.
- **Semantic/organizational wrapper** — a designer-created GROUP purely for organizing layers in the panel, with zero layout or visual meaning (this is extremely common and is exactly the shape of several bugs fixed this session — a wrapper whose only role is to exist between a real container and its real content).
- **Component instance wrapper** — an INSTANCE node is itself a wrapper around its overridden children, with the actual "meaning" defined by the component it instances, not its own geometry.

### 1.13 — A second raw-data source exists, with a different shape than the REST API

Everything in 1.1–1.12 above describes Figma's REST API. But this codebase has a second, real, currently-live raw-JSON producer: a companion Figma Plugin (`figma-plugin/code.js`) that serializes the canvas from inside Figma itself, using the Plugin API rather than the REST API. The two do not agree on field names (REST's `imageRef` vs. the plugin's `imageHash`), units (REST's radian `rotation` vs. the Plugin API's documented degrees), or completeness (the plugin never emits `layoutGrow`/`layoutAlign`/`primaryAxisSizingMode`/`counterAxisSizingMode` under any name). Any research or fix that treats "the Figma design model" as a single shape is implicitly REST-only — a real, exercised second input path into this exact compiler needs its own translation layer, not just a more complete reading of the REST spec. (Full evidence in Part 4.1.4.)

## PART 2 — Design Intent: why Figma's tree looks the way it does

This section explains *why* real designers produce the tree shapes Part 1/3 describe — which matters because several of the shapes that break our heuristics are not edge cases, they are the ordinary output of ordinary Figma workflows, and knowing the workflow behind a pattern is what makes it possible to classify the pattern's Skeleton role (Part 3) with confidence instead of guessing.

- **GROUP vs FRAME is often a speed choice, not a semantic one.** Figma's fastest path to combine layers is select-multiple → Cmd/Ctrl+G, which always produces a GROUP — a node type that (per Part 1.1's trait analysis) structurally cannot carry `layoutMode`, fill, or corner-radius the way a FRAME can. A designer reaching for a FRAME (or explicitly running "Add auto layout") is making a more deliberate structural choice. This is a *tendency*, not a guarantee — a FRAME can still carry zero layout meaning — but it means node TYPE is a legitimate, if imperfect, signal of intent that our pipeline currently doesn't weight at all (GROUP and FRAME are handled identically once past basic ingest).

- **"Add auto layout" is itself a tree-mutating command, which is why nested single-child wrappers are so common.** Running Figma's own "Add auto layout" on an existing selection inserts a *new* FRAME as the Auto Layout container, wrapping whatever was there before. Designers do this repeatedly while iterating (add layout, undo, try a different grouping, add layout again), and each pass can leave a shallow, now-meaningless wrapper behind if part of the selection changes later. This is a direct, mechanical explanation for a "wrapper" being organizational-only (Part 1.12's third case) — it's frequently a fossil of an edit history, not a deliberate structural decision, which is exactly why it carries no reliable visual properties of its own for a heuristic to key off.

- **A sibling "background rectangle" instead of a parent's own fill is usually a portability habit, not a deliberate layering decision.** Designers commonly draw the background as its own rectangle — behind the content, matching the container's box — rather than setting the parent frame's fill, because a shape can be copy-pasted between frames, duplicated from an older component, or independently blurred/shadowed without touching the children on top of it. This is the ordinary origin of the "decorative/chrome" role (Part 3.3): the rectangle is doing a job (background) that has nothing to do with why it exists as a separate layer (convenience/portability), and the two facts need to be told apart rather than one inferred from the other.

- **Component overrides are the single richest, most explicit intent signal Figma can produce — and we currently discard it entirely.** The whole point of a component system is that a designer changes one master and every instance updates automatically; when an instance's text, icon, or visibility genuinely needs to differ, Figma records that difference explicitly as an `override`. Semantically, an override says, in Figma's own words, "this specific per-instance choice was deliberate" — a far stronger and cheaper signal than trying to reconstruct the same fact by comparing an instance's rendered geometry against its sibling instances. Per Part 1.9/6.1, this is entirely unused today, not because it's hard to read, but because no real component-based fixture has ever been tested against the pipeline.

- **Freeform (no Auto Layout) files are not random — they correlate with when and by whom a file was authored.** Auto Layout existed for years before it became Figma's default recommended practice; files (or file sections) built early, built by designers trained before Auto Layout was standard, or built as quick low-fidelity mockups where reflow doesn't matter, are systematically more likely to be 100% absolute-positioned. This matters for generalization (Part 6): our fixture corpus being freeform-heavy is not necessarily representative of "most Figma files" in general — it may just be representative of *how these particular five files happened to be authored*, which is a narrower and less reliable population to have generalized a whole architecture from.

- **Icon-on-backdrop composites (Part 3.3's "composited overlay" role) come from a specific, common component-authoring pattern**: a small reusable "icon container" (colored circle/square + centered glyph) built once and instanced repeatedly, deliberately kept as two siblings rather than one merged shape so the backdrop's color and the icon's glyph can vary independently across instances (e.g. a green circle for "success," a red one for "error," same icon slot). The overlap our detector had to specifically guard against (Part 4.4-4.6's `hasGenuineInternalOverlap` gate) is not an accident of this pattern — it is the pattern; treating it as a sequence to flatten was always going to be wrong for this specific, common origin.

**On "can multiple hierarchies represent the same UI, and how often":** given the above, the honest answer is *routinely, and for mundane reasons* — not as some pathological edge case, but as the ordinary residue of how design tools get used iteratively over time (undo/redo, copy-paste between contexts, gradual adoption of Auto Layout, convenience habits like sibling-rectangle backgrounds). A compiler design that treats tree shape as reliably meaningful is, by construction, betting against how design tools actually get used day to day.

## PART 3 — Skeleton Research: a canonical Design Skeleton

### 3.1 — Restating the user's own triggering question, precisely

The question that escalated this from "fix another bug" to "stop and research" was: *"we got real nodes and data from Figma — Figma's data already tells us which element is center-aligned, which has a border — so why are we not able to carry that forward? Why are we missing some nodes?"*

Parts 1, 4, and 6 above answer the mechanical half of this ("here are specific properties read from the wrong place, or never read at all"). But there is a deeper, structural half the mechanical bugs are symptoms of, and it's the reason fixing each one individually keeps surfacing another: **our pipeline does not currently separate "what is this node's ROLE in the design" from "where does this node sit in Figma's raw parent/child tree."** NDG mirrors Figma's tree almost 1:1. Every detector we have (`rowSet`, `freeform-layout/detect.js`, component-detect's geometry rules) operates directly on that raw tree shape plus geometry — meaning **the compiler is, today, quite literally following hierarchy instead of understanding design**, exactly as the user suspected.

### 3.2 — Proof that hierarchy and design intent are different things

Section 1.12 already established that a GROUP/FRAME wrapper can mean at least four structurally different things Figma's own JSON never labels (Auto-Layout container, boolean/vector composition, purely-organizational layer, component-instance shell). Section 6.4 extended this: two designers building the *identical visual UI* can produce two different node trees, and this session's own bug list is largely a record of exactly that gap being hit in practice — a spurious zero-column group, a false-positive uniform-size match across an unrelated pair of rectangles, an icon-on-backdrop composite that needed a dedicated overlap gate to avoid being flattened into a sequence it isn't part of. **Every one of these was the same underlying event: a heuristic that assumed tree-shape ≈ design-intent got a tree shape that didn't match its assumption.** Adding a new heuristic per case (which is what has happened four times now, per the precedent timeline above) does not fix this — it just narrows the gap for the *specific* tree shapes tested so far, leaving the same class of gap open for the next one.

### 3.3 — The proposal: classify role once, independent of tree position, before any layout decision is made

A canonical Design Skeleton sits between NDG and every downstream detector (layout interpretation, component detection, freeform clustering, responsive analysis). Its job is to answer, for every node, **"what is this, semantically, in the design"** — not yet "how should it be positioned." Concretely, every node gets tagged with exactly one primary role:

| Role | Definition | Example | Consequence for downstream stages |
|---|---|---|---|
| **Content** | Carries information the design exists to communicate | TEXT with real characters; an IMAGE fill; a VECTOR used as a meaningful icon | Never eligible for flattening/discarding; always gets real DOM representation; always a candidate for accessibility text |
| **Decorative / chrome** | Exists to style a container, not to be independently meaningful | A background rectangle exactly matching its parent's box; a colored circle purely acting as an icon's backdrop | Candidate for *lifting* into the parent's own CSS (background-color/border/border-radius) instead of becoming its own DOM node — generalizes the `chromeBg`/`chromeCornerRadius`/`chromeStrokeCss` lifting this session's fixes already do ad hoc in `rowSetRowDecls()`/`freeformGroupMemberDecls()`, as a first-class Skeleton concept instead of a per-mechanism special case |
| **Structural / organizational wrapper** | A GROUP/FRAME whose own box/fill/stroke carry no visual meaning — exists purely to organize layers | A designer's "Card Contents" group with no fill, no stroke, box == union of children | Candidate for flattening: discard the wrapper node itself, re-parent its children directly, carrying forward only its geometric offset (if any) |
| **Repeating-group member** | One instance of a visually-repeated pattern (card in a grid, row in a table) | Each of 4 "Incentive" cards | Tagged ONCE, centrally — every downstream stage (spacing, alignment, responsive breakpoints) consults this single fact instead of each independently re-detecting "is this a repeat," which is exactly the duplicated, inconsistent work `rowSet` detection and `freeform-layout` detection currently do in parallel with no shared source of truth |
| **Composited overlay set** | Multiple siblings that together form one visual unit via overlap, not sequence | Icon glyph centered on a colored circle backdrop | Tagged as a single group explicitly EXCLUDED from sequential/flex flattening — generalizes the `hasGenuineInternalOverlap` IoU gate hand-built this session into a declared Skeleton fact instead of a rescue check bolted onto one detector |
| **Layout container (real)** | A node where Figma itself declares layout (`layoutMode` HORIZONTAL/VERTICAL/GRID) | Any Auto Layout frame | Downstream stages read Figma's OWN declared spacing/alignment/sizing directly (Part 6.2) — geometry-guessing is never invoked at all for these, closing the single largest gap found in this research |
| **Layout container (inferred)** | No Auto Layout declared; geometry suggests a row/column/grid arrangement | A freeform "row" of cards with no `layoutMode` | The ONLY place geometry-based clustering heuristics should ever run — explicitly scoped to nodes that have already failed the "real declared layout" check, rather than applied uniformly regardless of whether Figma already answered the question |

### 3.4 — Two properties every Skeleton node must carry, independent of role

**Provenance.** Every Skeleton node retains an explicit pointer back to the raw Figma node(s) it derives from: 1:1 for an untouched node, 1:many for a flattened wrapper (the wrapper's id plus the fact that it was discarded), many:1 for a composited-overlay group (all member ids, plus which one is the designated "chrome"). This directly targets the traceability failure behind several of this session's hardest-to-find bugs (`strokes` silently relocating between `ingest.js`'s and `build.js`'s node shapes; `textAlignHorizontal` silently read from the wrong JSON nesting level) — with explicit provenance, "does this property survive to the renderer" becomes a checkable question against a named source node, not something only discoverable by noticing the visual output is wrong.

**Reading order.** An explicit, independently-resolved field, computed once — not assumed from Figma's layer order (proven wrong: Challenge Arena's row-set layer order was 001/003/004/002, not visual top-to-bottom) and not assumed from raw geometry alone either (composited/overlapping content has no single well-defined "position"). Every stage that currently needs an ordering — `materialize-html.js`'s child emission, responsive re-stacking, any future accessibility tab-order work — consults this one resolved field instead of re-deriving order from whatever raw signal happens to be convenient at that stage, which removes an entire class of "renders in the wrong order on this file, but not that one" bugs before they can occur.

### 3.5 — Why this is the direct fix for "why are we missing nodes"

Under the current architecture, a node's fate (is it rendered standalone, lifted as chrome, flattened as a wrapper, or accidentally dropped) is an emergent side-effect of which detector's internal bookkeeping happens to claim it first (Part 6.5's collision risk). Under a Skeleton architecture, a node's fate is the direct, legible consequence of a role it was explicitly assigned, once, for a stated reason, with a stated source — nothing is ever "missing" without that being a visible, debuggable classification decision rather than a silent side effect of iteration order or an unmatched heuristic threshold.

## PART 4 — Information Preservation, Stage by Stage

### 4.1 — Raw Figma JSON → NDG ingest

Full audit performed against 3 real cached Figma REST API responses plus 12 more cached fixtures (1,160+ real nodes), and cross-checked against `figma-plugin/code.js` — a **second, structurally different raw-JSON producer** that feeds the exact same `ingest.js` (see 4.1.4). All findings below are grounded in copy-pasted real fixture values, not documentation.

**4.1.1 — The architectural shape of this stage.** `workingNodeFromRaw()` (`compiler/ndg/ingest.js:31-128`) is one large object literal. There is no named allowlist constant anywhere — **the object literal itself is the allowlist**: any `raw.*` key not explicitly named on one of its ~90 lines is invisible to every single downstream stage, forever, with no error, warning, or trace. This one fact explains the shape of nearly every finding below — the question "did we lose property X" always reduces to "is X's exact key, at its exact real nesting level, named literally somewhere in this one function."

**4.1.2 — Confirmed correct.** Identity/structural fields (id/name/type/visible/children), the primary box (`absoluteBoundingBox`), typography's `style.*` fields (fontSize/fontWeight/fontFamily/letterSpacing/lineHeightPx/textCase/textAutoResize/textAlignHorizontal/textAlignVertical — all of this session's earlier fixes, confirmed holding), `characterStyleOverrides`/`styleOverrideTable` (captured as an **opaque whole object**, which means fields nested inside it survive "for free" even with no explicit handling — confirmed concretely: a real per-character `hyperlink` override, `{"type":"URL","url":"mailto:..."}`, was found intact in a real fixture despite `ingest.js` having zero explicit knowledge of `hyperlink` as a concept), stroke basics (`strokeWeight`/`strokeAlign`/`individualStrokeWeights`), corner radius, opacity, rotation, and all Component/Instance identity fields (`componentId`/`overrides`/`variantProperties`/etc. — confirmed real, populated `overrides` data with actual `overriddenFields` lists).

**4.1.3 — The single largest completeness gap: 9 of Figma's Auto Layout fields are 100% absent, despite `layoutMode` itself being captured.** `primaryAxisSizingMode`, `counterAxisSizingMode`, `primaryAxisAlignItems`, `counterAxisAlignItems`, `layoutWrap`, `layoutGrow`, `layoutAlign`, `layoutSizingHorizontal`, `layoutSizingVertical` are never referenced anywhere in `ingest.js` — confirmed present with real, varying values in this codebase's own cached fixtures (e.g. `layoutSizingHorizontal: "FIXED"/"HUG"/"FILL"`, `counterAxisAlignItems: "CENTER"/"MAX"`). This is the ingest-side half of the single most consequential finding in this whole research effort (see 4.2.1 for the interpretation-side smoking gun this directly causes).

**4.1.4 — A second raw-JSON source exists in this repo, and it disagrees with the first on field names, units, and completeness.** `figma-plugin/code.js` is a companion Figma Plugin that serializes a design tree in its own shape — explicitly, per its own header comment, "the shape `server/figma-build.js` expects." `ingest.js` reads `raw.*` fields by name with no per-source translation layer, so it silently assumes one canonical raw shape. Confirmed concrete mismatches:
  - **Image assets**: the plugin emits `imageHash`; the real REST field (used pervasively downstream, including `imageRefOf()` in the renderer, Part 4.4) is `imageRef`. A plugin-sourced design's images can never resolve, silently, via this path.
  - **Rotation units**: REST sends radians (confirmed: real fixture values are exact fractions of π, and the renderer's own `rotation*180/Math.PI` conversion confirms the whole pipeline agrees on radians for REST input) — but Figma's Plugin API's own `rotation` property is documented in **degrees**. If a plugin-sourced document is ever fed through the same ingest → render path, rotation would silently come out wrong by a large, wrong-unit factor. (Flagged as a verified risk, not a proven live bug — no plugin-exported sample exists in-repo to confirm empirically.)
  - **Completeness**: the plugin serializer never emits `layoutGrow`, `layoutAlign`, `primaryAxisSizingMode`, or `counterAxisSizingMode` under any name, regardless of what `ingest.js` does or doesn't read — so even a full ingest.js fix for 4.1.3 would still see nulls for these four fields on any plugin-sourced file.
  This means **any future fix to `ingest.js` has to be checked against two different raw shapes, or it fixes one input path while silently leaving the other exactly as broken** — a single-source mental model is baked into every line of `workingNodeFromRaw()`, and it's one more reason the same bug shape keeps recurring: the fix that closes it for the fixtures on hand (all REST-sourced) may not close it for every real input path this codebase already accepts.

**4.1.5 — Confirmed, live, "reads a field that doesn't exist" bug — the same shape as the historical `textAlignHorizontal` bug, still present today.** `ingest.js:76` reads `raw.overflowDirection || raw.overflow || null` into `attributes.overflow`. **`overflowDirection` does not exist in any of the 15 real fixtures sampled.** The real field controlling per-node clip behavior is `clipsContent` (a plain boolean, confirmed present on every real FRAME/GROUP) — sitting right next to the wrong name being read, never referenced anywhere in `ingest.js`. This is proven to propagate all the way to a real, live downstream effect: `ir-experimental-renderer.js:970` computes `clips: node.attributes.overflow === 'HIDDEN'` for every node — since `attributes.overflow` is always `null` on real data, **`clips` is always `false`, for every node, regardless of the design's actual clipping.** (This combines with, and is the actual root cause behind, the separate rendering-stage finding in 4.4 below that `.clips` is only ever consulted for the page root — even that one consumer never gets a true value from real data, because the source was already wrong two stages upstream.)

**4.1.6 — Whole categories with zero capture, confirmed real and populated in this codebase's own fixtures:** `isMask`/`maskType` (high severity — see 4.2 for why this specifically breaks structural collapse), `booleanOperation` (a real `BOOLEAN_OPERATION`-type node with `booleanOperation:"EXCLUDE"` exists in-corpus), `blendMode` (present on every node; legacy `server/figma-generate.js:209-210` already has a correct CSS `mix-blend-mode` lookup table for this that was simply never ported into `ingest.js`), `strokeCap`/`strokeJoin`/`strokeDashes` (same pattern — legacy `figma-generate.js:94` already reads `strokeDashes` correctly), `textDecoration` (same pattern again — legacy already handles it), `cornerSmoothing`, `absoluteRenderBounds` (the effects-inclusive bounding box — needed for any node with shadow/blur bleed), `relativeTransform` (the only source of skew/non-uniform-scale — completely unmodeled anywhere as a result), `exportSettings`, `interactions`, `lineTypes`/`lineIndentations`/`listSpacing`/`paragraphSpacing`/`paragraphIndent`, `background`/`backgroundColor` (page/canvas-level fill, distinct from per-node `fills`). **A recurring sub-pattern worth naming explicitly: at least four of these (`blendMode`, `strokeDashes`, `textDecoration`, ELLIPSE roundness) already have correct, working handling somewhere else in this repository (legacy `server/figma-generate.js`) that was simply never carried into the current ingest/render pipeline** — these are not unsolved problems, they're unported ones.

**4.1.7 — Two structural inconsistencies worth flagging as process risks, not just data gaps:**
  - `paints` stays top-level on the working node, but `build.js` relocates `strokes` and `effects` into `attributes.strokes`/`attributes.effects` during final graph-node assembly, for no documented structural reason. Today's consumers have been updated to match, but any future code written by analogy with `paints` (the "obvious" sibling) will silently read `undefined`.
  - `compiler/ndg/ids.js`'s `graphChecksum` (`:41-51`) maintains a **second, independently hand-maintained field list**, separate from `build.js`'s `toNdgNode`. It happens to include `geometry`/`attributes` as whole nested objects today, so nothing currently under-hashes — but it means every future top-level field addition needs a manual, easy-to-forget matching edit here, or the "deterministic rebuild" guarantee this checksum exists to provide silently stops covering the new field.

**4.1.8 — There is no safety net that could have caught any of the above, by construction.** `compiler/ndg/validate.js` (full file read) checks exclusively structural properties: id/graph presence, duplicate ids, negative box dimensions, edge shape/reachability, cycles, orphans. **It never inspects the contents of `paints`, `geometry.*`, or `attributes.*` at all.** A graph where every single node has `attributes.textAlignHorizontal === null` and `attributes.overflow === null` (both real, confirmed, historical states) validates as `ok: true` with zero errors or warnings. The existing test suite's own assertions mirror this blind spot almost exactly (`compiler/test/ndg.test.js`'s "geometry + constraints + attributes preserved" test only ever checks `box.width`, `attributes.constraints.horizontal`, `attributes.layoutMode`, and `paints.length`) — meaning the test suite would not have caught a single one of the bugs found in 4.1.3, 4.1.5, or 4.1.6 either. This is a direct, structural explanation for "why do these bugs survive to production, repeatedly, undetected": nothing in the pipeline has ever been able to see them.

### 4.2 — Interpretation, Component Detection, and Freeform Clustering

Full audit of `compiler/layout/*`, `compiler/rulepack/*`, `compiler/components/*`, `compiler/freeform-layout/detect.js` (full, 517 lines), and the upstream `compiler/geometry/*` engine that actually performs the raw x/y/w/h clustering `layout/interpret.js` consumes.

**4.2.1 — THE smoking gun of this entire research effort: the code reads the wrong field, checks for values that can never appear there, and the correct field — with the exact values the code is looking for — sits unread in the same JSON.** `compiler/layout/interpret.js`'s `sizingAxis()` (`:51-63`) decides whether a node should behave like CSS `width:auto`/`fit-content`/`100%` by pattern-matching `node.attributes.constraints.horizontal`/`.vertical` for the substrings `'FILL'`/`'HUG'`/`'STRETCH'`/`'MIN'`. Direct inspection of 1,160 real nodes across this codebase's own cached fixtures confirms `constraints.horizontal`/`.vertical` **only ever contains**: `LEFT`, `RIGHT`, `CENTER`, `LEFT_RIGHT`, `SCALE`, `TOP`, `BOTTOM` — Figma's older, legacy *resize*-constraint vocabulary, which **structurally cannot ever contain** `FILL`/`HUG`/`STRETCH`/`MIN`. **This means `sizingAxis()`'s two most important branches are permanently dead code against every real Figma file that will ever exist** — the function can only ever fall through to `'fixed'` or `'unknown'`. Meanwhile, the *correct* field for this exact question — `layoutSizingHorizontal`/`layoutSizingVertical`, whose real, confirmed values are exactly `FIXED`/`HUG`/`FILL` — sits in the same raw JSON, one property over, and is never read by anything (root cause: dropped at ingest, per 4.1.3). This single finding is the clearest available proof that the compiler's problem is not "our heuristics need tuning" — it's "we are guessing at a question Figma already answers, using a field that was never capable of answering it."

**4.2.2 — Geometry-based clustering runs unconditionally, on every node, regardless of whether Figma already declares the answer — confirmed in all three independent clustering systems, and the one place that says otherwise is a comment, not a rule.** `compiler/geometry/detect.js`'s own header comment states: *"Never reads layoutMode/constraints — that is layout.interpret's job; this stage exists precisely for nodes where those are absent."* Tracing every call site confirms **no code anywhere checks `node.attributes.layoutMode` before this clustering runs** — `detectGeometry` runs on every parent with ≥2 children unconditionally, Auto Layout or not, and the same is independently true of `compiler/freeform-layout/detect.js` (confirmed via grep: zero references to `layoutMode` in the entire 517-line file). The claim in the comment is only true *in effect* — and only because of a second, independent coincidence: `layout/interpret.js` happens to score a declared `layoutMode` at 0.85 confidence against geometry hints capped at 0.4-0.6 (4.2.1's sibling finding), so declared data happens to win arbitration today. **Nothing structurally enforces this.** It is two separately-maintained scoring tables staying in the right relative order by chance, not by contract — a future change to either (e.g., a new geometry pattern scored at 0.9 to fix some other bug) would silently invert the priority with no test anywhere positioned to catch it. `docs/COMPILER_MIGRATION_BLUEPRINT.md` already recorded the original, correct version of this same diagnosis (*"nothing in `compiler/` computes row/column/grid/card/banner shape from sibling (x,y,w,h)... `layout/interpret.js` reads only Figma's declared fields"*) — confirming the geometry-clustering stage was explicitly conceived as a fallback-only mechanism, even though no code was ever written to actually confine it to that role.

**4.2.3 — Three independent implementations of the same clustering question, with three independently-maintained tolerance constants, and no shared source of truth.** `compiler/geometry/detect.js`, `compiler/rulepack/packs/component-detect/geometry-rules.js`, and `compiler/freeform-layout/detect.js` each re-cluster the *same* raw NDG sibling boxes from scratch — each with its own `indexGraph`/`childrenOf` tree-walk, and in at least two confirmed cases, literally duplicated constants (`ALIGN_TOL=2`/`GAP_TOL=2` and the `isRealOverlap` overlap-test function are both declared independently, verbatim, in two separate files, one comment explicitly noting this is "to keep this module independently requirable... without an import cycle"). This is a mechanical, structural explanation for exactly the pattern the user flagged as the trigger for this whole research effort: **a fix made in one clustering implementation (freeform-layout's IoU overlap gate, its alignment-tolerance gate, its vacuous-member gate) does not exist in the sibling implementations, because there was never one place to fix.** Concretely and currently unfixed: `compiler/rulepack/packs/component-detect/geometry-rules.js`'s `detectCardGridUniformity` has **no alignment/axis discrimination at all** (width/height-variance-only) — `freeform-layout/detect.js`'s own code comment explicitly names this exact weakness and works around it locally with its own `ALIGNMENT_TOLERANCE_FRACTION` gate — but `compiler/components/detect.js`'s own direct call into the same shared function has no such gate, and once `detectCardGridUniformity` claims a parent, row-set recognition is unconditionally skipped for it. **Net effect, confirmed and still open: three or more individually card-shaped elements stacked vertically (not side-by-side) will be misclassified by Component IR as a horizontal card grid**, with no test anywhere in the suite exercising this exact shape (existing tests only cover vertically-stacked *non-card-shaped* rows, which never reach this function because they fail its own precondition gates).

**4.2.4 — The mechanical explanation for "a border/corner-radius rendered on the wrong element."** None of the four audited detection systems ever reads `cornerRadius` itself (confirmed by grep — zero occurrences in any of them). What they produce instead is a `chromeId`/`contentIds` *node-identity* decision that a downstream renderer later uses to decide whose corner-radius/stroke/fill to read. `compiler/rulepack/packs/component-detect/geometry-rules.js` picks "the chrome" via silent first-array-match (`chrome[0]`) whenever more than one sibling passes the box-coverage "looks like a background" test, with no verification step. **A wrong pick here is invisible at the detection stage — it only ever manifests three stages downstream, as a visually wrong border or corner radius** — which is exactly the class of symptom (border-line issues, alignment issues) the user was independently spotting by eye in the rendered output before this research began, now with a plausible, precise upstream mechanism identified.

**4.2.5 — `childOrder` is always raw Figma paint/z-order, and is never reconciled with the spatially-correct order the pipeline already computes elsewhere.** `layout/interpret.js` sets a node's `childOrder` directly from the unmodified Figma children array for everything except the in-flow/out-of-flow split. `compiler/geometry/detect.js` internally computes genuinely spatial ordering (sorted by X/Y, or row-flattened for grids) while clustering — and then discards it, surfacing only a coarse string hint token. Concrete, confirmed failure mode: a designer duplicating a layer and dragging the copy to the front of the Figma layers panel (changing paint order, not visual position) produces scrambled HTML source order, with no code path to prevent it. Notably, `compiler/freeform-layout/detect.js`'s *own* member ordering **is** spatial — meaning two IRs computed from the same nodes can already disagree on order today. A working, general-purpose fix for this (`orderChildrenVisualY`, in `compiler/geometry/rules/structural-polish.js`) **already exists in this codebase** — it's simply wired only into one narrow, render-time "header cluster" special case, never into `layout/interpret.js`'s general `childOrder`. This is the third confirmed instance this research found of "the correct fix already exists somewhere in this repository; it was never applied generally" (the other two: 4.1.6's legacy blend-mode/stroke-dash/text-decoration handling, and the ELLIPSE-radius type-check pattern from Part 1.3/4.1).

**4.2.6 — Component overrides are geometrically invisible, in all three clustering systems, confirmed.** An override that hides one instance's badge, or lengthens its text enough to grow an auto-sized box, makes that one instance geometrically dissimilar from its otherwise-identical siblings — and none of the three clustering systems ever consult override data to compensate, because `compiler/components/detect.js` only ever extracts override *key names* (`overrideKeysFrom`), never the override's actual new *value* — so there is no way for any downstream system to distinguish "this override toggled visibility" from "this override changed a text string," even in principle. Confirmed via grep: instance/override data never flows into any of the three geometric clustering call sites at all.

**4.2.7 — No cross-check exists for a node playing two structural roles at once (member of one group, container of another).** `compiler/freeform-layout/detect.js`'s own code comment documents a real, previously-observed instance of exactly this collision (a card matched simultaneously as a legitimate 5-member group's member and as its own spurious 2-member container) — the shipped fix (a zero-column gate) suppresses only that one specific degenerate sub-case. A genuine nested repeating group — e.g., a testimonials section that is itself a row-set of quote blocks, each of which internally contains its own small repeating avatar+rating cluster — is confirmed, by inspection of the full 517-line emission loop, to have no reconciliation mechanism at all.

**4.2.8 — `SECTION` nodes are completely unhandled, confirmed across every detection system, despite reaching the pipeline's raw data today.** Grepping `compiler/layout/*`, `compiler/rulepack/*`, `compiler/components/*`, `compiler/freeform-layout/*`, `compiler/geometry/*`, and `compiler/ndg/*` for any `SECTION`-specific handling returns nothing — the only node-type checks anywhere in these systems are `COMPONENT`/`INSTANCE`/`TEXT`/`IMAGE`/`SOLID`. Meanwhile `figma-plugin/code.js` already explicitly lists `'SECTION'` in its own container-type array, confirming Section nodes do reach this codebase's raw data today — they are simply never distinguished from a plain FRAME/GROUP once ingested, and so are fully exposed to every false-positive clustering risk documented above.

### 4.3 — Freeform Layout IR → RenderNode → CSS/HTML (own knowledge, verified directly this session)

This part of the pipeline is `compiler/freeform-layout/detect.js` → `compiler/artifacts/ir-experimental-renderer.js` → `compiler/emit/render/css-declarations.js` → `compiler/emit/render/materialize-html.js`. Everything below was directly verified against real Figma fixtures this session, not inferred.

**What enters:** NDG graph nodes (each with `.box`, `.paints`, `.attributes.strokes`, `.geometry.{cornerRadius, rectangleCornerRadii, opacity, strokeWeight, strokeAlign, individualStrokeWeights, rotation}`, `.attributes.{textAlignHorizontal, textAlignVertical, textCase, ...}`).

**What this stage assumes (the actual architectural weakness, stated plainly):** `detect.js`'s whole job is to look at a set of sibling nodes with NO Auto Layout declared and guess, from raw geometry alone, whether they form a "repeating group" (cards, table rows) whose internal content can be safely flattened into a shared CSS grid. Every bug found and fixed today in this stage was a variant of the same root issue: **the clustering heuristics reason about uniform size, alignment, and position — but never asked "does this content have Figma's OWN Auto Layout data available instead of needing to be guessed at all," and never checked whether candidate "content" elements are actually meant to be sequential (stackable into a flat grid) versus genuinely composited/overlapping (like an icon sitting on a colored circle backdrop — two sibling shapes forming one visual unit, not a sequence).** Concretely, this session found and fixed:
- A false-positive group formed by matching two pixel-identical, unrelated background rectangles (uniform-size clustering compared height only, not width).
- A missing "cross-axis" content inset, because the clustering only ever computed position along ONE axis (whichever it needed for row/column bucketing) and never computed — or even represented a place to store — the perpendicular offset.
- Silently zero corner-radius/stroke/opacity/rotation/gradient/text-align on any node not specifically recognized as a "card" by an entirely separate, narrower Component-IR path — meaning the SAME visual property (a rounded, stroked, colored card) had two unrelated, inconsistently-complete code paths depending on which detector happened to recognize it first.
- A group whose "columns" resolved to zero (a structurally meaningless group) still got registered as a valid container, silently colliding with a *different*, legitimate group the same node also belonged to as a *member* — corrupting which of two structurally-identical sibling cards took which rendering path, for no reason traceable to the design itself.
- An icon and its colored-circle backdrop (genuinely overlapping sibling shapes) being flattened into a grid row, because nothing in the clustering ever tested candidate content for mutual overlap before deciding it was "sequential."

**The pattern underneath all of these:** this stage does not have a *concept* of "verify this is safe before flattening it" as a first-class, systematic step — each safety check (the IoU overlap gate, the vacuous-member gate, the zero-column gate) was added individually, after a specific failure was observed on a specific fixture, rather than derived from a general theory of what makes flattening safe. That is architecturally the same complaint the user is raising about the whole compiler, reproduced in miniature inside one file.

**RenderNode → CSS (`css-declarations.js`'s `modeDecls()`):** this function is the actual place every visual CSS property gets decided, and until today it read exactly: `fillCss` (single SOLID paint only — any gradient or multi-fill silently produced no background at all), `cornerRadius` (numeric only — silently blind to ELLIPSE-type roundness), `strokeCss`+`strokeWeight` (silently blind to `strokeAlign` CENTER/OUTSIDE — confirmed **244 of 290 real strokes in our own corpus are CENTER or OUTSIDE, not INSIDE** — and blind to per-side weights). Effects (shadows/blur), node-level opacity, rotation, and text-align were all ingested by NDG and never read by this function at all — not a geometry-inference problem, simply code that was never written for those specific properties, sitting right next to sibling properties (font-size, textCase) that WERE handled correctly using the identical pattern.

**Two confirmed cases of "the data is real, but is read from the wrong place":**
- `compiler/ndg/build.js` moves `strokes` from the working-node's top-level (where `ingest.js` puts it, matching `paints`) into `attributes.strokes` during final graph-node assembly, for no documented reason — any code written by analogy with `paints` (top-level) silently gets `undefined`.
- `compiler/ndg/ingest.js` read `raw.textAlignHorizontal`/`raw.textAlignVertical` at the top level, when Figma actually nests these under `raw.style` — exactly like `fontSize`/`fontWeight`/`textCase`, which the SAME file reads correctly from `raw.style` four lines above. This produced `null` on every single node, in every design, silently, for the entire time this field existed in the schema.

Both are evidence for the SAME conclusion Part 1.1 already stated architecturally: **we have no systematic contract for "where does property X actually live on a raw Figma node, and does it survive unchanged through every stage of our own pipeline" — each property's correctness has been established one bug report at a time.**

### 4.4 — Image & vector fill resolution (own knowledge, verified directly this session via grep/read)

`imageRefOf(node)` (`ir-experimental-renderer.js:196-198`) resolves a node's image by `(node.paints || []).find(p => p.visible !== false && p.type === 'IMAGE')` — **`.find()`, first match only**. Any node with a solid-color wash stacked over/under an image fill (a completely ordinary Figma pattern — see 1.4) silently keeps only whichever one happens to be first in the array; the other is dropped with no warning. There is no code path anywhere in the renderer that reads more than one paint per node for non-text nodes.

Separately, `svgForNode` (line 569) reuses the exact same `<img src>` render path for genuine vector nodes (VECTOR/icon/arrow paths) by having a **different, earlier stage** (`server/figma-generate.js`'s `reconstructSvgMarkup`) pre-render them to SVG markup, which then gets wrapped as a `data:image/svg+xml` URI and handed to the same `imageSrc` variable an actual Figma image fill would produce. This is a genuinely good piece of architecture — one render path serves two different Figma concepts cleanly — but it means **any diagnosis of "why did this icon render wrong" has to know to look in a completely different file** (a separate SVG-reconstruction stage, not the renderer or NDG at all), which is exactly the kind of cross-stage knowledge this whole research effort is trying to make explicit instead of tribal.

**Confirmed, verified gap:** `grep` across the entire `compiler/` tree for `imageTransform`/`scaleMode`/`object-fit`/`objectFit` shows:
- `imageTransform` (Figma's 2×3 matrix for `scaleMode: STRETCH` fills, i.e. an image cropped/panned/rotated within its frame independent of the frame's own box) — **zero matches anywhere in `compiler/`.** Not ingested, not read, not emitted. Any image using this (confirmed 7 real occurrences existed in the Challenge Arena fixture, per earlier-session findings) silently renders as a plain top-left-anchored image fill instead.
- `object-fit` — **exists only inside `compiler/emit/render/utility-css.js`**, exclusively as part of hand-authored, class-name-keyed utility rules (`.et-card__media { object-fit: cover }`, `.et-card__icon { object-fit: contain }`, `.et-banner__media { object-fit: contain }`) that only apply if a node was separately recognized as a "card"/"banner" by the legacy Component-IR detectors and given one of those exact class names. **`css-declarations.js`'s `modeDecls()` — the actual per-node CSS decision function for ir-experimental's generic rendering path — has zero references to `object-fit`, `isImageFill`, or `imageSrc`.** This means: any image-fill node NOT specifically recognized as a card/banner gets an `<img>` tag with no `object-fit` at all, and its visible cropping behavior is whatever the browser's default (`fill`, i.e. non-uniform stretch to the box) happens to produce — which will only visually match Figma's own `scaleMode: FILL` (Figma's own cover-equivalent) by coincidence, when the image's intrinsic aspect ratio already matches the box.

This is the same architectural pattern as Part 4.4-4.6's finding, generalized: **a real visual property (how an image fills its box) is handled correctly only inside a narrow, specifically-recognized pattern (card/banner), and silently falls back to a browser default everywhere else** — not because it's hard, but because the generic path was never given the same treatment as the specific one.

## PART 6 — Generalization / Stress Test

The user's framing for this section is exact: not "does this fix today's bug," but "what would break the compiler on the next 1,000 Figma files." Rather than one abstract list, this section separates stress cases by *why* they'd break something, since the fix for each category is different.

### 6.1 — Entire node types with zero code path (would not render as intended at all)

Confirmed via direct grep across `compiler/` (see Part 1.2): 20 of Figma's 28 real node types have never been exercised. The highest-risk gap is not exotic — it's the single most common real-world pattern:

- **Any file built from a real component library** (`COMPONENT`/`COMPONENT_SET`/`INSTANCE` with `componentProperties`/`overrides`/`variantProperties`) — professionally-maintained design systems are built this way almost universally, and our pipeline has never once processed one. Now confirmed precisely (Part 4.2.6): NDG's `ingest.js` does read `componentKey`/`componentId`/`overrides`/`variantProperties` correctly, but `compiler/components/detect.js` only ever extracts override *key names*, never the override's actual new *value* — and none of the three geometric clustering systems consult override data at all. Concretely: an instance whose override merely hides a badge or lengthens a headline becomes geometrically dissimilar from its otherwise-identical siblings to every clustering system we have, silently degrading a 6-card repeating group's recognized membership to 5 (or fewer).
- **`SECTION`** — increasingly common for organizing large canvases; unhandled.
- **`BOOLEAN_OPERATION`** — union/subtract/intersect/exclude vector combination; unhandled (would likely fall through to generic-group handling, losing the actual composed shape).
- **`TABLE`/`TABLE_CELL`** — real declared tabular structure. We have an entire heuristic subsystem (`rowSet` detection) whose job is to *guess* that a set of geometry-only siblings forms a table — and no code that reads Figma's own explicit `TABLE` node when the source file already declares one directly.

### 6.2 — Real, declarative Figma signals the compiler never reads even though geometry-guessing exists to approximate them

This is the sharpest category, because it's not "missing support for something exotic" — it's "actively re-deriving, by fallible inference, an answer Figma already gives for free":

- **`layoutMode: 'GRID'`** — a real, native Auto Layout mode with explicit row/column counts, gaps, and per-cell placement. Our own "grid-track" detection mode is 100% geometry-inference and has no awareness this native signal exists. A file using real Grid Auto Layout would be run through the same fragile clustering heuristics as a freeform file that never declared any layout at all.
- **`layoutSizingHorizontal`/`layoutSizingVertical`: HUG/FIXED/FILL** — Figma's own direct statement of "should this behave like CSS `width:auto`/`fit-content`/`100%`." This is no longer just "an approximation instead of reading the field" — it's now confirmed as this entire research effort's single clearest smoking gun (Part 4.2.1): the code that's supposed to answer this question checks a *different* field (`constraints.horizontal/vertical`) for values (`FILL`/`HUG`/`STRETCH`/`MIN`) that field can never structurally contain, while the field that actually has those exact values sits unread one property over.
- **`layoutPositioning: ABSOLUTE`** on an Auto-Layout child — Figma's own explicit "this one child opts out of the flow." Zero occurrences in our 5-file corpus, but on the next 1,000 files this is a completely ordinary pattern (e.g. a badge pinned to a card corner while the card's other children flow normally) and nothing reads this field at all today.
- **`counterAxisAlignItems: BASELINE`** — real text-baseline alignment mode; unhandled.
- **`gridChildHorizontalAlign`/`gridChildVerticalAlign`/`gridRowSpan`/`gridColumnSpan`** — per-cell placement inside a real Grid Auto Layout; unhandled (compounds with the `layoutMode: GRID` gap above).

The common thread: **our compiler was architected around "Figma didn't tell us, so we must infer," which is a defensible design for files without Auto Layout — but it is applied uniformly, even to files that DO declare the answer.** Every one of these is a case where the fix is not "build a smarter heuristic" but "check whether Figma already told us before reaching for a heuristic at all."

### 6.3 — Real visual properties silently dropped regardless of layout mode (would render, but wrong)

From Part 5's matrix, concretely: any node with more than one fill (e.g. a photo with a color-wash overlay — ordinary, not exotic), any `GRADIENT_RADIAL`/`GRADIENT_DIAMOND` fill, any shadow or blur effect, any blend mode other than Normal, any per-corner mixed radius, any skewed/non-uniformly-scaled node, any stroke with dashes/caps/joins, any `scaleMode: STRETCH` image with a real transform matrix, any list/paragraph-spacing text structure, any `textDecoration` beyond a bare underline. None of these are hard to imagine in a real marketing site, dashboard, or app design — they're arguably more common in *polished* professional files than in the rougher fixtures we've been testing against, which raises an uncomfortable possibility worth stating plainly: **our 5-file empirical corpus may be systematically under-representing exactly the kind of visual polish a compiler most needs to get right**, because a rougher/simpler design is less likely to exercise gradients, multi-fills, effects, and mixed corners in the first place.

### 6.4 — Structural ambiguity: same UI, different tree (would render inconsistently between two designers' files)

Per Part 1.12: a wrapper GROUP/FRAME can be an Auto Layout container, a boolean/vector composition, a purely-organizational layer with zero visual meaning, or a component-instance shell — and Figma's raw JSON never labels which. Two designers building the visually identical component could easily produce two different node trees (one flattens decorative backgrounds into the card frame's own fill, another leaves them as separate sibling rectangles) and there is no evidence anywhere in the current pipeline that both would reliably converge to the same output. This is precisely the pattern behind several bugs fixed this session (spurious zero-column groups, false-positive uniform-size clustering, genuine-internal-overlap needing a dedicated gate) — each one was a case where the *tree shape* differed slightly from what the heuristics implicitly assumed, and the visual result diverged as a consequence. Part 3 (Skeleton proposal) is the direct answer to this category; it is the category the user's own triggering question ("why are we missing some nodes") was about.

### 6.5 — Compounding risk: detection order and cross-mechanism collisions

Confirmed this session: a node can simultaneously be a candidate for row-set detection, freeform-group-membership, and generic geometry-mode interpretation, with the actual rendering path decided by whichever mechanism's internal bookkeeping (a `Map`/`Set` keyed by node id) gets populated or checked first — the zero-column spurious-group bug corrupted a *different, legitimate* group purely by accident of iteration order, not because of anything in the design itself. On the next 1,000 files, as more detection mechanisms accumulate (each added to solve one prior gap — see the six-mechanism history above), the number of possible pairwise collisions between them grows faster than the number of mechanisms, not linearly. This is an argument, independent of any single missing property, for why "add a fifth detection mechanism" is a materially worse bet than consolidating onto one representation that each existing mechanism's logic can be rewritten to consult (Part 3/7).

### 6.6 — Three risks confirmed live and unfixed today, not hypothetical (from the layout/component-detection audit)

Unlike most of this section, these three are not "what could go wrong on a future file" — they are confirmed, present, currently-unfixed gaps in the exact code this compiler runs today:

- **Three or more card-shaped elements stacked vertically will be misclassified by Component IR as a horizontal card grid.** `compiler/rulepack/packs/component-detect/geometry-rules.js`'s `detectCardGridUniformity` has no alignment/axis discrimination at all — `compiler/freeform-layout/detect.js` already knows this (its own code comment names the exact weakness) and works around it locally with its own alignment-tolerance gate, but `compiler/components/detect.js`'s direct call into the same shared function has no such gate, and once a parent is claimed as a card grid, row-set recognition is unconditionally skipped for it (Part 4.2.3). No test in the suite exercises vertically-stacked *card-shaped* siblings.
- **A genuine nested repeating group has no reconciliation mechanism.** `compiler/freeform-layout/detect.js`'s own comment documents an already-observed case of one card matching simultaneously as a legitimate group's member and as its own spurious container; the shipped fix suppresses only that one degenerate sub-case. A testimonials section that is itself a repeating row of quote blocks, each internally containing its own small repeating avatar+rating cluster, would hit the same collision with no gate to catch it (Part 4.2.7).
- **A wrong "which sibling is the chrome" pick is invisible at detection time and only manifests three stages later as a visually wrong border or corner radius.** None of the four detection systems reads `cornerRadius` itself — they decide node *identity* (`chromeId` vs `contentIds`) via silent first-array-match with no verification, and a downstream renderer only later reads whichever node was picked. This is a plausible, mechanical explanation for exactly the border/alignment symptoms the user was spotting by eye before this research began (Part 4.2.4).

## PART 7 — Recommendations

### 7.1 — Research Document
This file. Sourced from Figma's official REST API schema, three exhaustive agent audits (NDG ingest, layout/component/freeform detection, existing-docs survey), and direct grep/read verification of every claim that could be checked against this codebase's own source and cached real fixtures.

### 7.2 — Design Skeleton Proposal
Part 3. Core idea: classify every node's *role* (content / decorative-chrome / structural-wrapper / repeating-group-member / composited-overlay / real-layout-container / inferred-layout-container) once, as an explicit, provenance-tracked fact — independent of where the node happens to sit in Figma's raw tree — before any layout decision is made. This is the direct, structural answer to the question that triggered this research ("why are we missing nodes we have real data for").

### 7.3 — Information Preservation Matrix
Part 5. ~50 properties classified ✓/⚠/✗, each with a file:line citation or a confirmed-via-real-fixture-data note — not an estimate.

### 7.4 — Missing Concepts (the highest-value gaps, ranked)

1. **Nine Auto Layout sub-fields** (`primaryAxisAlignItems`, `counterAxisAlignItems`, `layoutWrap`, `layoutGrow`, `layoutAlign`, `primaryAxisSizingMode`, `counterAxisSizingMode`, `layoutSizingHorizontal`, `layoutSizingVertical`) — 100% absent from NDG despite being real, populated, and exactly what several existing heuristics are trying (and structurally failing) to approximate. Cheapest possible fix-to-impact ratio in this entire document: these are ingest-layer, additive, zero-architecture-change reads (Part 4.1.3, 4.2.1).
2. **A canonical node-role concept** (the Skeleton, Part 3) — without it, "is this a background, a wrapper, or real content" is re-guessed independently by (at least) three separate clustering implementations, per design, forever.
3. **Real Component/Instance/variant handling** — data survives ingest today but nothing downstream consults override *values*, and no clustering system tolerates the geometric variation a legitimate override introduces (Part 4.2.6).
4. **A second raw-data source (the Figma Plugin path) with its own translation requirements** — not previously accounted for in any architecture document surveyed; own field names, own units, own completeness gaps (Part 1.13, 4.1.4).
5. **Whole categories with zero code path**: `SECTION`, `BOOLEAN_OPERATION`, `TABLE`, masks (`isMask`/`maskType`), effects (shadow/blur), blend modes, multiple stacked fills, radial/diamond gradients, per-side stroke cap/join/dash, `absoluteRenderBounds`, `relativeTransform`/skew.
6. **Reading/source order as its own resolved concept**, independent of both raw paint-order and pure geometry (Part 4.2.5).
7. **Property-level validation** — nothing in the existing test suite or `validate.js` can detect a systematically-null or wrongly-sourced field; every bug in Part 4.1/4.2 would pass all existing checks today.

### 7.5 — Architectural Weaknesses (the mechanisms that produce recurring gaps, not any single missing property)

1. **NDG's ingest is an unlabeled allowlist with no negative-space visibility.** `workingNodeFromRaw()`'s object literal IS the complete list of what the rest of the compiler can ever see; anything not named is invisible with no error, forever (Part 4.1.1).
2. **Whole nodes, not just fields, can be silently deleted.** `hasPaintSignal()`'s blind spots (opacity/rotation/mixed-radius not checked) mean a structurally "empty" wrapper can be carrying real, invisible visual meaning that gets deleted along with it — this is a stronger failure mode than a dropped field, because there's no node left to even inspect afterward (Part 5, "Node fate on collapsed wrapper nodes" row).
3. **Three independent geometric clustering implementations, no shared source of truth, tolerance constants literally duplicated verbatim in places.** A fix in one (freeform-layout's IoU gate, alignment gate, vacuous-member gate) structurally cannot benefit the other two, because there was never one place to fix (Part 4.2.3) — this is the single most direct mechanical explanation for "fix one bug, another appears in a different section."
4. **"Figma's declared data beats geometry-guessing" is an emergent coincidence between two separately-maintained scoring tables, not an enforced rule.** Nothing stops a future edit to either table from silently inverting this (Part 4.2.2).
5. **Geometry-based clustering runs unconditionally**, regardless of whether the target node already has reliable Auto Layout data — confirmed in every clustering system audited, contradicting these systems' own header comments about when they're supposed to run (Part 4.2.2).
6. **Silent first-match tie-breaks decide node identity with no verification** (e.g., "which sibling is the chrome"), and the consequence only becomes visible 2-3 pipeline stages later as a wrong visual property — making root-causing a rendered bug genuinely hard without knowing this mechanism exists (Part 4.2.4).
7. **No cross-check exists for a node holding two structural roles at once** (group member and container simultaneously) — a real, previously-observed collision has only a special-cased suppression, not a general reconciliation (Part 4.2.7).
8. **The renderer actually shipped (`ir-experimental`) violates its own architecture's documented contracts** ("never read NDG directly," "never recompute layout") by re-materializing its own NDG and running its own full detection stack rather than consuming previously-computed IR (confirmed via direct source inspection, Precedent section).
9. **No safety net exists that could catch any of the above mechanically.** `validate.js` and the existing test suite are close to 100% structural; a graph where every node has a systematically-null or wrongly-sourced property validates cleanly (Part 4.1.8).
10. **This exact diagnosis has been made six times in seven days, each followed by a new bounded mechanism rather than a change to what the compiler retains from the source file** (Precedent section) — meaning the standing risk isn't "will we misdiagnose this again," it's "will the response to this document be a seventh mechanism."

The key design decision this makes explicit: **the three existing clustering implementations (`compiler/geometry/*`, `compiler/rulepack/packs/component-detect/*`, `compiler/freeform-layout/*`) are retired INTO the Skeleton stage, not left standing alongside it as a fourth parallel system.** Every fix any of them has accumulated (IoU overlap gates, alignment tolerance, vacuous-member rejection, chrome/content separation) is real, hard-won knowledge that the Skeleton stage should absorb — this is a consolidation, not a rewrite from zero.

### 7.7 — Estimated Implementation Roadmap

This project's own document history (Precedent section) shows six consecutive "implemented" or "fixed" claims that did not close the gap they targeted — so this roadmap deliberately avoids calendar-time estimates in favor of dependency-ordered phases with an explicit proof-of-done for each, matching `docs/COMPILER_MIGRATION_BLUEPRINT.md`'s own stated (but not-yet-honored) principle that *"every phase's exit criterion is a clean dual-run report, not a written status doc."*

- **Phase B — Build the property-level safety net (7.5.9) before building anything else new.** A golden-fixture test that asserts real values for every property in Part 5's matrix, run against the actual cached Figma fixtures already in this repo. - **Phase D — Migrate the renderer to consume the Skeleton + existing IR stages**, closing the confirmed architecture-contract violation (7.5.8) where the current renderer re-materializes its own NDG instead of consuming previously-computed IR.
- **Phase E — Deliberately expand the fixture corpus** to include a component/instance-based file, a Plugin-API-sourced file, and at least one file exercising `SECTION`/`TABLE`/`BOOLEAN_OPERATION` — Part 6 identified all of these as structurally under-tested, not just currently-imperfect.

## PART 9 — Absolute Positioning Audit

Every site in the ACTIVE renderer (`compiler/artifacts/ir-experimental-renderer.js` + `compiler/emit/render/css-declarations.js` — the renderer this whole session, and every session in the Precedent table, has actually been debugging) that emits `position:absolute`, a hard `left`/`top`, or a hard/min `width`/`height`. Legacy path (`server/figma-generate.js`/`figma-build.js`) audited separately once the parallel research pass returns (9.5).

### 9.0 — The headline finding: the fix already exists, and is never called

`compiler/layout/interpret.js`'s `sizingAxis()` was fixed earlier in this project specifically because it was reading the wrong field (Part 4.2.1's "smoking gun": it checked `constraints.horizontal/vertical`, which structurally can never hold `FILL`/`HUG`/`FIXED`, instead of `layoutSizingHorizontal`/`layoutSizingVertical`, which does). That fix is correct and shipped — `interpretNode()` (interpret.js:206-209) now computes, for every node, a genuinely accurate `sizing: { horizontal: 'fill'|'hug'|'fixed'|'unknown', vertical: ... }` straight from Figma's own explicit intent.

**That value is never read.** `ir-experimental-renderer.js:717` does `const interp = interpByNodeId.get(node.id)`, and this exact `interp` object has its `.padding` (line 843) and `.gap` (line 842) fields read two lines apart — but `.sizing` is not referenced anywhere in the file (confirmed: zero matches for `.sizing`, `sizing.horizontal`, `sizing.vertical`, `interp.sizing` in `ir-experimental-renderer.js`). The fix for "this compiler doesn't know a Figma node is supposed to be responsive (FILL) vs. content-sized (HUG) vs. intentionally fixed (FIXED)" was made in the interpretation stage and then silently orphaned one stage before it could matter. This is the single most consequential finding in this document: **the data needed to stop emitting hard pixel widths already exists, correctly computed, in every render pass that has run since the `sizingAxis()` fix shipped — it has simply never been wired to the code that writes CSS.**

This single wiring gap is the direct, provable root cause of both of today's reported bugs:
- **The hero-row overflow** (`section-section-light`, node 43:3): the row's own `layoutSizingHorizontal` is almost certainly `FILL` (it was captured filling exactly the 1192px content width of a 1440px canvas) — had the renderer read `interp.sizing.horizontal === 'fill'` it would emit `width:100%`/`flex:1` instead of `min-width:1192px`, and the row would shrink fluidly with `.et-page` instead of overflowing it the moment the viewport is narrower than the original design canvas.
- **The `Group 357` misalignment** (`.group-272`): rendered `position:absolute; left:139px; top:97px; width:1646px` — a hard pixel box with no relationship to its parent's actual rendered width. Whatever this node's real `layoutSizingHorizontal`/`layoutAlign` says, it is not consulted; the box is reproduced as a literal, non-fluid copy of one specific canvas measurement.

### 9.2 — Direct trace: does this explain `Group 357`?

The DevTools evidence you captured shows `.group-272 { position: absolute; left: 139px; top: 97px; width: 1646px; min-height: 712px; }`, wrapping 2 flex sub-groups and 2 raw `<img>` siblings. Two independent things are visible in that one rule, matching two different rows in 9.1:

2. `width:1646px` as a hard, non-fluid pixel value — per 9.0/9.1's `css-declarations.js:583-588` row, this is the min-width-from-captured-box mechanism, completely blind to whatever this node's real `layoutSizingHorizontal` says. ### 9.3 — Legacy renderer comparison

A parallel research pass audited every other absolute-positioning site in the codebase, live or not, including the legacy pre-`ir-experimental` path. Full findings below; the single most important one changes this document's priority roadmap (Part 12.5).

**Everything outside the active renderer's own two files turned out to be either legitimate or dead code.** `compiler/layout/interpret.js`'s own absolute-classification (`isAbsolutePositioning`/`absSelf`/`absChildren`) is correctly gated on Figma's real `layoutPositioning:ABSOLUTE` signal and defaults signal-less nodes to `'unknown'`, never `'absolute'` — no overreach. `compiler/layout/project.js`, `compiler/layout/constraint/{solver,network}.js`, and `compiler/features/extract.js` all contain absolute-positioning logic that is **never actually called by the live pipeline** (`ir-experimental-renderer.js` gets its recognition hints from `compiler/geometry` instead, and calls `interpretGraph` directly — it does not go through `project.js`/`constraint/*` at all). `compiler/emit/render/utility-css.js`'s `RESPONSIVE_STANDARDS_BLOCK`/`DUAL_PATH_STANDARDS_CSS` (badge overlays, centered glyphs, the `.et-path-b__stage` scaled-artboard fallback) is a byte-for-byte port of legacy CSS kept only for potential diff-parity — **nothing imports it**; only the position-free `CSS_RESET_BLOCK` from that file is actually wired into `materialize-html.js`. `compiler/emit/render/materialize-html.js`'s only absolute-related logic is reactive plumbing (establishing `position:relative` on a container that has an absolute child, so that child doesn't anchor against an unrelated ancestor) — not a decision site.

**The genuinely significant finding is the comparison between the two legacy files, `server/figma-generate.js` and `server/figma-build.js`** — because it turns out the CODE THIS PROJECT ALREADY HAS (but doesn't run) is more sophisticated about this exact problem than the code it actually ships today:

- **`server/figma-generate.js`** is absolute-heavy *by explicit, stated design* (its own header: "Auto-layout frames → flexbox; freeform frames → absolute positioning") — any child of a non-Auto-Layout parent unconditionally becomes `position:absolute`, no recovery attempt at all.
- **`server/figma-build.js`** wraps that absolute baseline in what the audit calls "a large, deliberate anti-absolute-positioning machine": roughly ten named, sequenced recovery passes — `applyFlexColumnFromBoxes` (conservative: only fires when flexing reproduces the *exact same* box positions), `liftArtboardContent`, `demoteAbsoluteFlexStacks` (its own comment: *"Flex/grid containers must not stay absolutely positioned — that is the artboard anti-pattern"*), `inferColumnFlex` (confidence-scored, threshold-gated), `collapseCardShells`, `collapseBannerShells`, `stampFeatureCards`, `inferCardGrids`, `recoverSectionHeaders`, `inferSideBySideRows`, `normalizeSectionShell`, `normalizeSiblingCardChrome` — each converting recognized absolute-positioned content into flex/grid. What survives all of them unrecovered falls to an explicit, named last resort ("Path B" / `server/dual-path.js`): a scaled, absolutely-positioned artboard snapshot, reserved for genuinely unrecognizable freeform content or an explicit pixel-fidelity QA mode — not a silent default.

**This means the "seventh mechanism" this document's own Precedent section worried about (Part 0) may have been an unnecessary rebuild in at least one respect**: `ir-experimental` (mechanism #4) was built because the officially-"Live" IR pipeline had zero sibling-geometry code (Precedent row 5) — true, and its own `compiler/geometry`/`compiler/freeform-layout` clustering is real, working, hard-won logic (Parts throughout this document). But `figma-build.js`'s ten pattern-specific recovery passes are a DIFFERENT, larger body of prior art than what `ir-experimental` reinvented, sitting unused in the same repository. `collapseCardShells`/`collapseBannerShells`/`recoverSectionHeaders`/`normalizeSiblingCardChrome` in particular have no clear analogue in `ir-experimental`'s current pattern coverage (Part 10's taxonomy). Before building any NEW pattern-specific recovery logic, the cheaper move is checking whether `figma-build.js` already solved it — ported, not reinvented (Part 12.5, Phase A3, added below).

Part 1 catalogs Figma's *node* types; this catalogs the *composed UI patterns* real designers build with them, since a compiler can be 100% correct about every individual node and still misrender the pattern those nodes form together (a hero section is not just "a frame with a heading and an image" — it is a specific compositional convention). For each: how Figma-native data signals it, what IR should represent it, and which renderer strategy is appropriate. "Current" reflects this codebase's actual behavior, not aspiration.

|---|---|---|---|---|

| **Masonry (variable-height tiled columns)** | No native Figma layout mode maps to CSS masonry (CSS itself only has masonry via `grid-template-rows:masonry`, not yet broadly supported) — in Figma this is almost always hand-placed absolute/freeform | Falls to the general freeform-clustering path | Freeform clustering into per-column Y-bands is architecturally the right approach (this is exactly what `compiler/freeform-layout/detect.js` already does for repeating cards) — no new IR needed, just correct application | Not distinguished from ordinary repeating-card grids; likely works by coincidence when column heights happen to be uniform, unverified for genuinely variable-height masonry |

| **Mixed Auto Layout + absolute-override child** (`layoutPositioning:ABSOLUTE`) | A child of a real Auto Layout parent explicitly opted OUT of the flow | Read correctly at `interpret.js:14-18`, and is the one case Part 9.1 confirms is legitimate | `position:absolute` relative to the flex/grid parent (a real, supported CSS combination — flex/grid containers are valid positioning contexts) | Confirmed correct when it fires; **zero real occurrences observed in this project's fixture corpus to date** (Part 5) — untested on a real file, not proven broken |

**The pattern that recurs across this table**: of the ~14 rows, at least 6 (Hero, Timeline, Overlay, Navbar/Sidebar pinning, Floating elements, Dashboard-via-freeform) don't need a NEW pattern-specific mechanism at all — they need Part 9's sizing-intent fix and a `constraints`-to-CSS-anchoring translation. Only 2 rows (Grid-via-wrap, native `TABLE`) represent a genuinely unhandled Figma signal with no existing partial mechanism.

## PART 11 — Responsive Strategy

The user's own framing: *"Our compiler currently generates left, top, fixed width, fixed height. This is unacceptable."* This part proposes when each CSS layout mechanism should be chosen, and reconciles that against what `compiler/responsive/*` already does (Part 8's Responsive row: a real breakpoint/strategy IR exists and does reach literal `@media` CSS — this is NOT starting from zero).

### 11.1 — Decision order (proposed)

For each node, in this priority order — matching the "Figma's declared data beats geometry-guessing" rule Part 7.5.4 already establishes as intended-but-unenforced:

1. **`layoutPositioning:ABSOLUTE`** → `position:absolute` relative to its real Auto Layout parent (Part 10's "Mixed" row). Rare, legitimate, already correctly read.
2. **Real Auto Layout (`layoutMode`) present** → `display:flex`, direction from `layoutMode`, **and** sizing per node from `layoutSizingHorizontal/Vertical` (Part 9.0): `FILL`→`flex:1 1 0`/`width:100%` as axis-appropriate, `HUG`→no explicit size (content-driven, CSS's own default), `FIXED`→the current hard/min-pixel behavior, unchanged. This ONE change is what turns the hero row and `Group 357`'s wrapper from non-fluid to fluid.
3. **Real Grid Auto Layout (`layoutMode:'GRID'`)** → `display:grid`, already correctly wired (task history #38).
4. **No Auto Layout, but `constraints` present** (Part 10's Navbar/Sidebar/Floating rows) → derive `position:sticky`/`position:fixed`/percentage-anchored offsets from `constraints`, instead of raw pixel `left`/`top`. Currently `constraints` is read only as a `sizingAxis()` fallback (interpret.js:78-85) — never for its own actual purpose.
5. **Real geometric overlap between siblings, no Auto Layout at all** (Part 10's Overlay row) → `position:relative` container + `position:absolute` children, but with offsets expressed as `%` of the container's own box (computable today: `(child.x - parent.x) / parent.width * 100`) rather than raw pixels, so the composition scales instead of only being correct at exactly one canvas width.
6. **No Auto Layout, no constraints, no overlap** (genuinely freeform, single item or simple list) → normal block flow; this is the case existing `orderChildrenVisualY`/Skeleton reading-order work already targets correctly (Part 4.2.5).
7. **Last resort**: raw pixel `position:absolute;left;top;width;height` exactly as today, for whatever doesn't match 1–6. Per Part 9's audit, this should become a small residual, not (as it effectively is today, since dimensions in flex/grid children ALSO end up as hard pixels via `min-width`) the de facto universal fallback regardless of which of the 6 cases above actually applies.

### 11.2 — When to generate which CSS mechanism

| Situation | Generate | Not | Why |
|---|---|---|---|
| Node has `layoutSizingHorizontal:'FILL'` inside a flex row | `flex:1 1 0` or `width:100%` (axis-dependent) | `min-width:<captured px>` | Matches Figma's own explicit "grow to fill" intent; today's behavior instead floors it at whatever width it happened to have at ONE canvas size |
| Node has `layoutSizingHorizontal:'HUG'` | No explicit width (let flex/content size it); `flex:0 0 auto` if inside a row that also has FILL siblings, so it doesn't get stretched | any hard width or min-width | "Hug" is Figma's own "size to content" — imposing any captured pixel value overrides the one case where CSS's natural behavior already matches Figma's intent for free |
| Node has `layoutSizingHorizontal:'FIXED'` (or the field is absent — legacy/plugin-sourced file) | Today's `min-width:<captured px>` behavior | — | This is the one case where today's behavior is already correct; the fix is additive (branch on the other two values), not a wholesale replacement |
| Real `constraints` pin one edge, opposite edges scale (`LEFT_RIGHT`/`TOP_BOTTOM`) | Percentage-based inset (`left:Npx; right:Npx`) instead of a fixed `width` | Fixed pixel width | This is Figma's own explicit "this element should stretch when its parent resizes" signal — currently indistinguishable in output from a node that should NOT stretch |
| Genuine z-order overlay, no Auto Layout | `position:absolute` with `%`-based offsets (11.1 case 5) | Pixel offsets | Keeps the composition correct across viewport widths without needing a new breakpoint entry per overlay |
| A breakpoint/strategy adaptation already computed by `compiler/responsive/detect.js` | Literal `@media` block (already wired, Phase 4) | — | Already correct; not a gap |
| Aspect-ratio-locked media (an image/video whose Figma `scaleMode` implies a fixed ratio) | CSS `aspect-ratio: W / H` + fluid width, rather than hard pixel width AND height | Hard px width + height (today's `hardImageSize` behavior) | `aspect-ratio` lets the image scale fluidly with its container while preserving proportion — today's hard-both-dimensions approach (added to fix the "avatar renders at native pixel size" bug, Part 9.1) solved one bug by introducing exactly the "no fluid relationship to parent" problem this Part exists to close |

### 11.3 — Container queries / intrinsic sizing

Figma has no design-time concept of "how this component should look at different CONTAINER widths independent of viewport width" — Auto Layout's HUG/FILL/FIXED is the closest analogue, and it is a per-node property, not a per-container query. **Container queries are therefore not a translation target for anything in Figma's own data model** — they would only become relevant if this compiler ever synthesized genuinely responsive COMPONENT variants (e.g., a card that lays out differently below 300px of available width) from multiple Figma breakpoint frames of the same component, which is a design-process convention some teams use but nothing in this codebase's ingest currently correlates across frames to detect. Out of scope until that correlation exists; not a near-term gap.

### 12.0 — Why an 8th new file still breaks (direct answer)

Restating the question precisely: *if this diagnosis ("compiler guesses instead of reading Figma's declared intent") was already correctly made 6 times before 2026-07-29, and a 7th time in Part 1–7 of this same document, why did a NEW file (`Group 357`, 2026-07-31) still break, in the same category, 2 days later?*

## PART 13 — Compiler-Theoretic Reframing: Figma as a Source Language

Parts 1–12 diagnosed this project's problems in *this project's own* vocabulary (NDG, LayoutIR, Skeleton). This part asks a different question: if this is genuinely a **compiler** — Figma as source language, browser rendering as target machine — what does 70+ years of compiler-construction practice say about the shape it should have, and does that framing predict failures this document hasn't found yet?

### 13.0 — Why this reframe is legitimate, and precisely where it stops being one

The analogy is not decorative. A compiler is, structurally, any system that (a) parses a structured input into a representation that makes its MEANING explicit rather than just its shape, (b) verifies and normalizes that meaning through one or more intermediate forms, and (c) lowers the verified meaning to a different, lower-level target representation whose own execution semantics the source format doesn't share. That is exactly what "Figma JSON → CSS/HTML" is: two representations that share no execution model (a design tool's z-ordered, arbitrarily-nested canvas vs. a browser's box-model-and-flow rendering engine), bridged by exactly the kind of "does this source construct mean flex, grid, or absolute" decision a real compiler makes about "does this source construct mean a jump, a call, or a phi node."

Where the analogy has a real, honestly-stated limit: a programming language's grammar is **unambiguous by construction** — a parser either accepts a token stream or rejects it, and if it accepts, there is exactly one meaning. A Figma canvas has no such guarantee — Part 2 of this document ("Design Intent") already established that two designers can produce visually identical output from structurally different trees, and Figma itself enforces no rule that a "card" must be built one specific way. This means the "front end" of this compiler will **always** retain a genuine inference/heuristic component that a real language parser does not need — geometry-guessing cannot be fully eliminated, only correctly *subordinated* to declared intent when declared intent exists (Part 11.1's decision order already does this; this section explains why that specific ordering — not "always infer" or "never infer" — is the theoretically correct answer). Similarly, "verification" here can never be as absolute as LLVM's IR verifier, because there is no single formally-specified "correct" pixel output the way there is a formally-specified x86 instruction encoding — CSS rendering itself has browser-to-browser variance. Verification in this domain is necessarily closer to a **linter with strong invariants** than a **proof-checker**, and 13.4 below is scoped accordingly.

### 13.1 — The canonical pipeline, and where this project's actual code sits on it today

A generic compiler: `Source text → Lexer → Token stream → Parser → AST → Semantic analysis (binding + type-checking) → attributed/typed AST or a separate typed IR (HIR) → mid-level IR (MIR, usually a CFG in SSA form) → optimization passes (IR→IR) → verification → instruction selection / codegen → target machine code`.

| Compiler stage | This project's stated equivalent | What actually exists today |
|---|---|---|
| Source text | Raw Figma REST/Plugin JSON | Exists, two dialects (Part 1.13) |
| Lexer / token stream | — | No equivalent needed; JSON is already tokenized by its own grammar |
| Parser → AST | `compiler/ndg` (NDG) | **This is where the mapping already breaks.** NDG (Part 4.1) is lossless field-capture — closer to a **concrete syntax tree (CST)**, which preserves every literal token including ones with no semantic weight, than an AST, which is supposed to discard syntax and keep only meaning. Nothing in this pipeline currently plays the AST's actual role: grouping raw nodes into semantically meaningful units (*this is a card*, *this is decorative chrome*, *this is a real container*) BEFORE any layout decision. Part 3's proposed Skeleton is the correct fix — in this framing, **the Skeleton is not a nice-to-have, it is the missing parser output**. A pipeline that goes from a CST straight to codegen is, in compiler terms, a pipeline with no parser — it is structurally unsurprising that it produces inconsistent results, the same way a "compiler" that pattern-matches machine code directly out of a raw token stream would. |
| Semantic analysis (binding + type-checking) | — (does not exist as a distinct stage) | This is Part 12.2's proposed "Sizing/Positioning Resolution" layer, and Part 9.0's finding is precisely a **semantic-analysis-stage bug**: `interp.sizing` is a correctly-computed TYPE JUDGMENT (fill/hug/fixed is exactly as meaningful, structurally, as inferring a variable's static type) that never got attached to anything downstream — the equivalent of a type-checker that runs, produces a correct answer, and then the code generator ignores the symbol table entirely and re-derives types from raw syntax. In compiler terms this specific bug class has a name: **codegen bypassing the checker**, and it is a well-known category of miscompilation bug (seen historically in exactly this shape in several real compilers when an AST-to-bytecode lowering pass was written before a later type-checker pass, and nothing enforced that codegen could only run after checking populated the fact table it depends on). |
| HIR / typed AST | — | No equivalent; see above — this is the same missing stage as "semantic analysis," since this pipeline currently has no typed intermediate form of a node at all, only raw + heuristically-detected facts bolted on as side maps (`cardByNodeId`, `freeformMemberFact`, etc. — Part 4.2.3's "duplicated tolerance constants, no shared source of truth" finding is precisely what happens when a compiler has no canonical typed-AST slot to put a fact once and have every later pass trust it). |
| MIR (CFG, SSA) | LayoutIR / ComponentIR / ResponsiveIR | These exist and ARE real, structured intermediate forms (Part 7.6 already treats them as reusable) — but Part 7.5.8 confirms the ACTIVE renderer doesn't consume them; it recomputes everything from NDG directly. In compiler terms: **a real MIR exists, and the actual code generator doesn't lower from it — it re-runs its own ad hoc front end and skips straight to codegen.** This is architecturally equivalent to an LLVM backend that ignores the LLVM IR it was handed and re-parses the original C source itself. |
| Optimization passes (IR→IR, composable, single-purpose) | Scattered special cases inside `buildRenderNode()` | `ir-experimental-renderer.js`'s `buildRenderNode` is roughly 1,400 lines doing parsing-equivalent work (grouping), checking-equivalent work (sizing/role decisions), optimizing-equivalent work (wrapper collapse, cross-inset correction), AND codegen-adjacent work (assembling `layoutChoice`) — all in one function, one pass, one undifferentiated stage. Real compilers deliberately split these into small, single-purpose, independently-testable passes over a STABLE IR specifically because a monolithic pass makes it impossible to unit-test "does sizing resolution work" independent of "does wrapper collapse work" — which is exactly why this document's own fixes this session had to be verified via full end-to-end fixture regeneration every time (Part 4/12's discipline), rather than a narrow, fast unit test on one pass's output, the way a real compiler's `-passes=mem2reg` can be tested in complete isolation from every other pass. |
| Verification (between passes, before codegen) | — (does not exist) | Confirmed absent, Part 7.5.9/12.0. See 13.4 — this is the one genuinely NEW mechanism this reframing proposes. |
| Instruction selection / codegen | `css-declarations.js`'s `modeDecls()` et al. | Structurally the right SHAPE (a decl-emission function per IR construct) but, per Part 9's audit, currently making real SEMANTIC decisions at this stage (hardcoded `align-items`, unconditional `min-width` regardless of sizing intent) that a real backend would never make — instruction selection chooses HOW to implement an already-fully-decided IR operation, it does not decide WHAT the program means. Every case in Part 9.1's table where codegen is filling in a decision the front end should have already made (because the front end computed it and didn't pass it along, per 13.1's HIR/MIR row) is, in compiler terms, a **layering violation**. |
| Target machine code | CSS + HTML | The browser's rendering engine is the literal "target machine" — its layout algorithms (block/inline/flex/grid formatting contexts) are the "instruction set," and just as a real ISA has instructions that are cheap/native (flex, grid, block flow) vs. ones that exist but should be reserved for cases nothing else fits (absolute positioning — Part 9's "last resort, not default" finding, restated: **absolute positioning is this target's equivalent of hand-written inline assembly** — sometimes the only correct tool, never the default code path a well-behaved compiler reaches for first). |

### 13.2 — Lessons from each named compiler, and the one concrete principle each contributes

Generic descriptions of these compilers are widely available; the value here is naming the ONE actionable principle each contributes to this specific project, not summarizing their whole architecture.

- **LLVM.** Principle: *one stable IR, many frontends, many backends, and a mandatory verifier between passes.* LLVM IR's entire value proposition is that Clang, Rust, Swift can all target it, and any of LLVM's ~100 optimization passes can run on IR from any of them, because every pass trusts the SAME IR shape and the verifier guarantees that shape's invariants hold before the next pass runs. This project's three duplicate clustering mechanisms (Part 7.5.3) are the direct violation of this principle — they are effectively three different "IRs" for the same design-graph concept, none of which the other two passes can consume, forcing every new heuristic to be re-implemented three times or drift out of sync. **Action for this project: one canonical Skeleton/MIR shape, one verifier, retire the duplicates (Part 3/7.6, unchanged) — LLVM is the strongest existing proof this specific consolidation is the industry-standard answer to this exact symptom, not a novel or risky proposal.**
- **Swift compiler (SIL).** Principle: *a mid-level IR can exist specifically to preserve source-language semantics that the FINAL target IR would discard too early.* Swift doesn't lower straight from its typed AST to LLVM IR — it introduces SIL specifically because LLVM IR has already forgotten concepts like "this is a protocol witness table" by the time optimizations run on it, and some Swift-specific optimizations (and ALL of Swift's diagnostics — definite-initialization checking, etc.) need that semantic information intact. This maps directly onto why "just emit CSS a bit smarter" is the wrong framing: this project needs a mid-level representation that still knows "this was Figma's `FILL` sizing intent" and "this was a real Auto Layout container" — concepts CSS itself has no name for — resolved and preserved through the pipeline, not re-derived from geometry at the last second the way `ir-experimental-renderer.js` currently does. **The proposed "Sizing/Positioning Resolution" layer (Part 12.2) is, precisely, this project's SIL — a mid-level IR that exists ONLY to keep Figma-specific semantic facts alive long enough for codegen to use them.**
- **TypeScript compiler.** Principle: *separate BINDING (name/scope resolution) from CHECKING (semantic/type analysis) from EMITTING (a composable pipeline of small AST-to-AST transformer passes), and prefer declared types over inference whenever a declaration exists.* The Binder/Checker split is why TypeScript can type-check incrementally and why "what does this identifier refer to" is answered exactly once, in one place, for the whole program. This project currently answers "what is this node's role/sizing" independently, differently, in up to three places per Part 7.5.3 — the Binder/Checker split's lesson is that this should be answered once, attached to the node, and treated as authoritative everywhere after. TypeScript's emit pipeline (a linear sequence of small, composable `Transformer` functions, each doing ONE downlevel transform) is also a good literal template for what Part 12.2's proposed "MIR → CSS" stage should look like structurally, rather than the current monolithic `buildRenderNode`.
- **Rust (HIR/THIR/MIR).** Principle: *whole-program dataflow analysis (borrow-checking) is deliberately performed on a control-flow-graph-shaped MIR, not on the AST, because CFG form is what makes dataflow analysis tractable — and it is done in exactly ONE place, on exactly ONE canonical MIR, never per-frontend-construct.* This project's row-banding/overlap/side-by-side detection (Part 4.2.3, Part 7.5.3) are ALL, precisely, dataflow analyses over sibling geometry (a fact about node N depends on facts about its siblings, propagated through a graph) — currently implemented as three separate ad hoc tree-walks rather than one canonical graph representation with one shared analysis. **Rust is the strongest available proof that "dataflow analysis needs a graph-shaped canonical IR, not three independent tree-walks" is correct, load-bearing compiler-design practice, not an abstraction for its own sake.**
- **Babel.** Principle (a genuine, useful COUNTEREXAMPLE): *a single-AST, visitor-pattern transform pipeline is the RIGHT architecture specifically when source and target are the same language at roughly the same abstraction level (JS-to-JS).* Babel has no separate mid-level IR because it doesn't need one — down-leveling `const` to `var` doesn't require forgetting-then-reconstructing semantic information the way crossing from "Figma's Auto Layout" to "CSS flexbox" does. **The lesson is a warning, not a template: `ir-experimental-renderer.js`'s current single-monolithic-pass shape is architecturally appropriate for a Babel-style same-level transform — and this project is not one. Its problems are symptomatic of using a Babel-shaped architecture for a Swift/Rust-shaped problem (crossing a real semantic-domain boundary), not a coincidence.**
- **ESBuild / SWC.** Principle: *when a transform pipeline IS Babel-shaped (homogeneous, same-level), reimplementing it in a systems language for raw throughput is a legitimate, well-proven strategy — but it inherits Babel's own architectural ceiling, it does not raise it.* Neither tool introduces new IR layers versus Babel; both are evidence that "more IR stages" is a correctness/semantic-preservation tool, not a performance one, and that performance work belongs AFTER the correctness architecture is right, not instead of it. Relevant caution for this project: any future "let's just make the renderer faster" effort should not be mistaken for solving the problems this document identifies — ESBuild is proof that raw speed and semantic correctness are orthogonal axes.
- **Clang.** Principle: *keep the AST maximally source-faithful (preserving even things codegen doesn't need, like exact macro expansions and comments) specifically because MULTIPLE DIFFERENT CONSUMERS beyond the compiler proper — clangd, static analyzers, refactoring tools — need to work from the same tree.* This project already has, or will soon want, multiple consumers of its own canonical design representation beyond the renderer: an accessibility auditor, a design-QA/pixel-diff tool, a future second renderer (e.g. React-component output instead of static HTML) — all of which Part 3's Skeleton proposal should serve equally, not just `ir-experimental-renderer.js`. **Action: design the Skeleton's shape around "what would a design-linter or a React-codegen consumer need from this tree," not narrowly around what today's one CSS renderer happens to read** — Clang's own history (its AST long outlived any single consumer it was originally built for) is direct evidence this pays off.

### 13.4 — The one genuinely new mechanism: `verifyIR()`

Modeled directly on `llvm::verifyModule()` — a single pass that walks the fully-resolved IR immediately before codegen and asserts a fixed list of invariants, failing loudly (not silently degrading) if any is violated. This is a NEW deliverable, not a restatement of Part 7.5.9's "we need a safety net" — it is a concrete first invariant list, derived directly from bugs this document has already found:

1. **Every node has exactly one resolved sizing strategy** (`fill`/`hug`/`fixed`), never `undefined`/`null` by the time codegen runs — this single invariant, if it had existed, would have caught Part 9.0's dead-`interp.sizing` bug the moment it was introduced, mechanically, rather than requiring a user to notice a rendered overflow on a specific fixture weeks later.
2. **Every node is a member of at most one repeating-group/card-cluster detector's output** — directly targets Part 7.5.3's confirmed duplication risk (three independent clustering mechanisms with no shared source of truth); a node claimed by two different detectors simultaneously is a real, checkable defect, not a matter of taste.
3. **A node with `position:absolute` in its resolved IR has a real, non-synthetic positioned ancestor within its Skeleton subtree** — targets the exact failure class `materialize-html.js`'s reactive `hasAbsoluteChild` plumbing (Part 9, background-audit section) exists to paper over; verifying it as an invariant catches the cases that plumbing doesn't.
4. **No node's resolved `mode` is `'unknown'` inside a Skeleton-classified real-Auto-Layout container** — directly targets the exact bug class fixed in task history #43 (leaf-inside-real-Auto-Layout absolute-positioning bug); as an invariant, it would have failed loudly on the very first fixture that exhibited it, rather than requiring the avatar-overlap screenshot report that actually surfaced it.
5. **Every effect/paint/stroke field consumed at ingest has a corresponding emission-stage consumer, or is explicitly annotated as intentionally structural-only** — this is the general form of Part 8's entire "ingested but never emitted" bug class (gradient text, object-fit, box-shadow — all fixed this session, all initially found only by a human noticing a rendered discrepancy). A build-time (not runtime) lint pass cross-referencing `ndg/ingest.js`'s field list against every read-site across the renderer would catch the NEXT instance of this exact bug class before it ships, not after a screenshot report.

Consistent with 13.0's honesty section: this is explicitly a linter, not a proof-checker — it cannot prove the OUTPUT is pixel-correct (no such proof is available for CSS the way `verifyModule` can prove IR well-formedness against LLVM's fully-specified grammar), but each invariant above is a mechanically-checkable, zero-false-positive structural fact whose violation has, in this document's own evidence, corresponded 1:1 with a real shipped bug every single time.

### 13.5 — How this changes the roadmap (Part 12.5)

One addition, no reordering: **`verifyIR()`'s first invariant (5-item list above) should be built ALONGSIDE Phase A0 (Part 12.5), not after it.** Per 13.0/13.4's own reasoning: a wiring fix with no verifier is exactly as unprovable, at the architecture level, as the original unwired `interp.sizing` was — this document can assert Phase A0 fixes the hero-row/`Group 357` class of bug for the FIXTURES it was tested against, but per 12.0's own finding (a correct fix in isolation from its consumer went unnoticed for an entire pipeline stage's lifetime), the only way to make that claim for the NEXT file, mechanically rather than by hoping a user reports it, is invariant #1 above running automatically on every future compile.
